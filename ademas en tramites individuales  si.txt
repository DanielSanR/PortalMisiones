● Excelente observacion, es el problema de diseño mas importante del proyecto. Pensemos esto bien.

  El problema
                                                                                                                                                                                    Un tramite como "Obtener licencia de conducir" tiene:
  - Contenido fijo (titulo, descripcion, requisitos generales) — igual en toda la provincia                                                                                       
  - Contenido por localidad (costos, contacto, horarios, quiza formularios) — cambia entre Posadas, Obera, Iguazu

  Esto impacta en tres dimensiones: modelo de datos, carga en backoffice y roles/permisos.

  ---
  Opciones de modelado

  Opcion A: Tramite base + tabla de contenido por localidad

  tramites (base)
    ├── titulo, resumen, descripcionLarga   ← fijo, provincial
    ├── requisitos                          ← fijo, provincial
    ├── formularios                         ← fijo (o por localidad, configurable)
    │
    └── tramite_contenido_localidad (overrides)
          ├── tramite_id + localidad_id (PK compuesta)
          ├── costos                        ← por localidad
          ├── contacto                      ← por localidad
          ├── sitioWeb                      ← por localidad
          ├── horarios                      ← por localidad
          └── urlTramite                    ← por localidad (el link de "Iniciar tramite" puede variar)

  Logica del portal: al seleccionar localidad, busca override. Si no existe, muestra el contenido base (fallback).

  Ventaja: Esquema claro, queries simples, facil de entender para quien carga.
  Desventaja: Si a futuro una seccion mas se vuelve "por localidad", hay que migrar.

  ---
  Opcion B: Todas las secciones como filas (EAV)

  tramite_secciones
    ├── tramite_id
    ├── localidad_id    (NULL = contenido base/default)
    ├── tipo            ('requisitos' | 'costos' | 'contacto' | 'formularios' | 'sitioWeb')
    ├── contenido       (TEXT o HTML)
    └── orden           (para controlar posicion del acordeon)

  Ventaja: Totalmente flexible. Cualquier seccion puede ser por localidad o no.
  Desventaja: Queries mas complejos, la carga en backoffice es mas confusa, perdes validacion de campos.

  ---
  Opcion C: Hibrida (recomendada)

  Separar en dos cosas claras: lo que es provincial y lo que es local.

  -- Tramite: contenido provincial (fijo)
  CREATE TABLE tramites (
    id                UUID PRIMARY KEY,
    titulo            VARCHAR(255) NOT NULL,
    slug              VARCHAR(255) UNIQUE NOT NULL,
    resumen           TEXT,
    descripcion_larga TEXT,
    requisitos        TEXT,            -- Guia de Requisitos Generales
    formularios       TEXT,            -- Formularios e instructivos
    url_oficial       TEXT,            -- URL default (fallback)
    organismo_id      UUID NOT NULL,
    modalidad_id      INTEGER NOT NULL,
    categoria_id      INTEGER NOT NULL,
    destinatario_id   INTEGER,
    icono             VARCHAR(50),
    estado            VARCHAR(20) DEFAULT 'borrador',
    destacado         BOOLEAN DEFAULT false,
    created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  );

  -- Contenido localizado: lo que cambia por localidad
  CREATE TABLE tramite_localidades (
    id              SERIAL PRIMARY KEY,
    tramite_id      UUID NOT NULL REFERENCES tramites(id) ON DELETE CASCADE,
    localidad_id    INTEGER NOT NULL REFERENCES localidades(id),
    costos          TEXT,              -- Costos y modalidad de pago
    contacto        TEXT,              -- Contacto (direccion, telefono, email)
    sitio_web       TEXT,              -- URL del organismo local
    url_tramite     TEXT,              -- "Iniciar tramite" especifico de la localidad
    horarios        TEXT,              -- Horarios de atencion
    notas           TEXT,              -- Info adicional local
    activo          BOOLEAN DEFAULT true,
    UNIQUE(tramite_id, localidad_id)
  );

  La regla es simple: si el campo puede ser distinto entre Posadas y Obera, va en tramite_localidades. Si es igual en toda la provincia, va en tramites.

  ---
  El problema de roles y carga

  Aca esta la decision clave. Hay dos modelos posibles:

  Modelo 1: El organismo gestiona todo (simple)

  SUPERADMIN          → todo
  ADMIN_ORGANISMO     → tramites de su organismo, TODAS las localidades
  EDITOR              → carga contenido de su organismo, TODAS las localidades

  Carga en backoffice:
  1. El editor crea el tramite (contenido provincial)
  2. En el mismo formulario (o en una tab/seccion aparte), agrega variantes por localidad
  3. Seria algo tipo: "Agregar contenido para localidad" > selecciona Posadas > carga costos, contacto, etc. > repite para Obera

  Pros: Simple, menos roles, un organismo es dueño de toda su informacion.
  Contras: Un organismo grande (ej: Ministerio de Transporte) tiene que cargar datos de 75 localidades. Mucho laburo para un equipo chico.

  ---
  Modelo 2: Edicion delegada por localidad (mas escalable)

  Agrega un nuevo rol y un campo de localidad al usuario:

  SUPERADMIN              → todo
  ADMIN_ORGANISMO         → tramites de su organismo, todas las localidades
  EDITOR                  → contenido provincial de su organismo
  EDITOR_LOCAL (nuevo)    → SOLO contenido localizado de su organismo + localidad

  -- Usuarios ahora tiene localidad opcional
  ALTER TABLE usuarios ADD COLUMN localidad_id INTEGER REFERENCES localidades(id);

  Carga en backoffice:
  1. EDITOR crea el tramite base (titulo, requisitos, formularios — lo provincial)
  2. EDITOR_LOCAL de Posadas entra al tramite y carga/edita costos, contacto, horarios de Posadas
  3. EDITOR_LOCAL de Obera hace lo mismo para Obera
  4. Cada uno solo ve y edita la pestaña de su localidad

  Pros: Escala bien. Cada oficina local carga su propia info. Menos errores.
  Contras: Mas complejo, mas usuarios que gestionar, requiere coordinacion.

  ---
  Mi recomendacion

  Arrancar con Modelo 1 (organismo gestiona todo) + preparar la estructura para Modelo 2.

  Concretamente:

  1. Modelo de datos: Usar Opcion C (hibrida) desde el principio. La tabla tramite_localidades ya queda lista.
  2. Roles ahora: Mantener los 3 actuales (SUPERADMIN, ADMIN_ORGANISMO, EDITOR). El organismo carga todo.
  3. UI del backoffice: En el formulario de tramite, agregar una seccion/tab "Contenido por localidad" donde se pueden agregar N variantes. Cada variante = una localidad + sus   
  campos (costos, contacto, etc.).
  4. Preparar para el futuro: Agregar localidad_id como campo nullable en usuarios desde ahora. No lo usas todavia, pero cuando quieras pasar al Modelo 2, solo tenes que agregar 
  un EDITOR_LOCAL al enum de roles y filtrar en el guard.
